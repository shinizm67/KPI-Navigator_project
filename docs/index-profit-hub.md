# 利益ハブ（旧 Index）コンセプト

更新日: 2026-04-26

## 位置づけ

- **Daily（フロート）**: 読み取り専用。**目標売上に対する実績（収入側の照合）**を主目的とする。
- **利益ハブ（グローバルメニュー「利益」/ EN: Profit）**: **プロプラン向け**。**収支の詳細と利益（PL 観点）を読み取り専用で参照**する場所とする。
- **Basic プラン**: 本ハブは利用不可。メニューからは **プラン変更（Change Plan）** へ誘導する。

## 画面内の呼称（デザイン用）

プレースホルダーおよび将来のセクション名のたたき台:

| 案（JA） | 案（EN） | 内容イメージ |
|---------|---------|-------------|
| 日次利益 | Daily profit | 日単位の収支・利益サマリー（読み取り専用） |
| 月次利益 | Monthly profit | 月単位の収支・利益 |
| 年次利益 | Annual profit | 年単位の収支・利益 |

旧称の「日次／月次／年次**収支**」から「**利益**」へ寄せることで、Daily の「目標対実績」と役割がぶつかりにくくなる。

## FL（Food & Labor）

- **FL** は **Food & Labor**（材料費と人件費）の略。売上に対する **材料費比率・人件費比率**、およびその合算（FL%）として KPI 化することが多い（飲食など）。
- **Food** は発注・小口などと突合しやすい一方、**Labor（特にアルバイト変動費）** は割増・休憩・時間粒度などで複雑になりやすい。専用ページ・法域テンプレ・CSV 連携の整理は **`docs/part-time-labor-cost.md`** を参照。

## 技術メモ（静的サイト時点）

- プロ向け URL: `app/profit/index.html`（JA）、`en/app/profit/index.html`（EN）。
- **プラン判定**: `sessionStorage` または `localStorage` のキー `kpiNavigator.subscriptionTier` が `'basic'` のとき、メニュー「利益」クリックで `setting/change_plan.html` へ遷移。値が未設定または `'pro'` のときは利益ハブへ遷行（開発時は未設定＝プロ扱い）。
- 認証・課金バックエンド接続後は、サーバ側の契約状態を正とし、上記はフォールバックまたは廃止する。

## 設計メモ：利益ハブ「3カード」本実装（2026-07-19・要合意）

### 現状把握

- ハブ本体は **静的 HTML**：`app/profit/index.html`（JA）／`en/app/profit/index.html`（EN）。ビルド生成物ではない（PL 表のような Python ビルダー経由ではない）。
- `.profit-hub-cards`（`<ul>`）に 4 カード：
  1. **損益表（PL）** … `a.profit-hub-card`（実装済み・`pl/index.html` へリンク）
  2. **日次利益** … `span.profit-hub-card.is-placeholder`「準備中（読み取り専用）」
  3. **月次利益** … 同上
  4. **年次利益** … 同上
- カード CSS はページ内 `<style>`（`.profit-hub-card` / `.is-placeholder` / `.profit-hub-card-note`）。Office モード対応あり。
- 利益の集計ロジックは既に存在：`scripts/pl_insight_data_client.py` → **`window.__plInsight`**（`localStorage` のみ読む自己完結 IIFE）。`monthMetrics(year,mi)` / `dayMetrics(year,mi,d)` が `income/expenses/fixed/expected/profit` を返す。**ただし現状は PL 表ページにしか注入されていない**。
  - 依存：日次の月次配分に `window.__plPreviewMonthlyExpenseAllocation`（配分エンジン）を使用。月次/年次の集計は月合計ベースで足りるが、**日次利益（今日）だけは配分エンジンが必要**。

### ゴール / スコープ（案）

「準備中」の3カードを **読み取り専用の実データカード**にする。各カードに当該粒度の**利益額（と粗利率など）**を表示し、可能なら詳細ビューへ誘導する。

- **日次利益**：今日の利益（＝今日の収入 − 今日の支出）。
- **月次利益**：今月の利益（今月の収入 − 支出）。
- **年次利益**：今年 YTD（または年計）の利益。

### 実装方式の選択肢

- **案A（軽量・ナビのみ）**：数値は出さず、各カードを詳細へのリンクにするだけ。日次→（年次/月次ページの「Daily」フロート）／月次・年次→`pl/index.html`。
  - 長所：最小・低リスク。短所：「読み取り専用の利益サマリー」という当初意図（数値表示）を満たさない。
- **案B（推奨・実数カード）**：`__plInsight` 相当を**ハブページにも注入**し、各カードに**実際の利益額**を表示（読み取り専用）。
  - 長所：意図どおり。短所：ハブへ集計モジュール＋配分エンジンの移植が必要。
- **案C（案B＋粗リンク）**：案B のカードを `pl/index.html` へのリンクにもする（現状は粗リンク。URL ハッシュ deep-link は後述③が入ったら精緻化）。

→ **推奨は案C**（数値表示＋粗リンク）。deep-link（該当 Area を開く）は **URL ハッシュが 2026-07-19 に実装済み**（`pl/index.html#insight=areaN&date=YYYY-MM-DD`。詳細は `docs/pl-insight-final-adjustments-memo.md`「② URL ハッシュ」節）。カードのリンクを粗リンク→ deep-link へ精緻化可能。

### カード表示内容（案C の具体案）

| カード | 主数値 | 補助 | リンク先（今回） |
|--------|--------|------|------------------|
| 日次利益 | 今日の利益 ¥ | 粗利率 %（利益/収入）／No Data 時「—」 | `pl/index.html`（将来: PL分析 Area1 当日） |
| 月次利益 | 今月の利益 ¥ | 粗利率 %／No Data「—」 | `pl/index.html`（将来: PL分析 当月 Area3） |
| 年次利益 | 今年 YTD 利益 ¥ | 粗利率 %／No Data「—」 | `pl/index.html`（将来: 年計） |

- **No Data 表現**：`docs/pl-insight-final-adjustments-memo.md` の共通ルールに準拠（ラベルは残し、値は「—」、レイアウトは崩さない）。
- **通貨**：JA=¥／EN=$（既存 `formatMoney` 準拠）。
- **年計 vs YTD**：年次カードは「YTD（今日まで）」か「年計（12ヶ月見込み含む）」か要合意（推奨：YTD＝確定分のみ）。

### 技術方針（案B/C 実装時）

- ハブは静的 HTML なので、集計は **インライン `<script>`** を追加して対応（PL 側の `__plInsight` はインライン生成のため import 不可）。
  - 選択肢1：`pl_insight_data_client.py` を**共有 .js に切り出し**、PL ハブ双方で読み込む（クリーンだが影響範囲大）。
  - 選択肢2：ハブ用の**小さな集計スクリプト**を新規に書く（月次/年次は月合計ベースで配分エンジン不要／日次のみ配分エンジンを別途注入）。
  - → 今回は影響を抑えるため **選択肢2（ハブ専用の軽量集計）** を推奨。まず月次・年次を実装し、日次は配分エンジン注入とセットで続けて実装。
- **ライブ更新**：`storage` / `kpi:*` イベントで再計算（PL 側と同様）。ハブは他タブでの入力変更を反映できると良い（任意）。
- **プラン判定**：本ハブ自体が pro 限定（既存の `subscriptionTier` ゲート）。カード個別の追加ゲートは不要。
- **JA/EN 両方**を同時更新（静的 2 ファイル）。

### 未決（合意したい点）

- (a) 方式は **案C（数値＋粗リンク）** で良いか（それとも案A の軽量ナビだけ／案B の数値のみ）。
- (b) 年次カードは **YTD**（確定分）で良いか（年計見込みは出さない）。
- (c) 補助表示は **粗利率（利益/収入）** で良いか（他に出したい指標は？）。
- (d) 実装順は **月次→年次→日次**（日次は配分エンジン注入とセット）で良いか。
- (e) リンクは今回 `pl/index.html` への粗リンクで良いか（deep-link は③ URL ハッシュ実装後に精緻化）。
