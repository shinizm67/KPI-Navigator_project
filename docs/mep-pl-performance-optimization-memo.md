# MEP & PL 軽量化メモ（漸進的最適化の方針）

## 0. このメモの位置づけ

MEP（Monthly Edit Page）・PL（損益表）は KPI Navigator の**サブスク ¥3,000/月の要となる機能群**。
機能追加を続ける中で表示・操作が重くなってきているため、「**後で一気に軽量化してデータを壊す**」事故を避ける目的で、
**今から“軽くしやすい形”で書き進めるための方針**を残す。

**大原則:** 大改修は機能が一段落してから、検証スクリプトを盾に**小さい単位で刻む**。
新規コードは最初から下記のエコノミックな書き方を癖づける（追加コスト ≒ ゼロ）。

---

## 1. 最大の武器：検証スクリプト（安全網）

`scripts/verify_pl_*.py` / MEP 側の検証が「**壊れていないこと**」を自動確認できる状態にある。
これがあるため「**挙動は同じ・中身だけ速く**」を機械的に担保できる。

- 既存の主な検証:
  - `verify_pl_year_totals.py`（年計列）
  - `verify_pl_occupancy.py`（家賃・物件選択）
  - `verify_pl_row_reorder.py`（行並べ替え）
  - `verify_pl_scroll_freeze.py`（縦スクロール固定・行高同期）
  - `verify_pl_reference_budget.py` / `verify_pl_reference_budget_l2.py`（参考予算 L1/L2）
  - `verify_pl_l2_toggle.py`（L2 トグル・行高拡張/縮小）
- **運用ルール:** 機能を足したら検証も足す。最適化のたびに全 verify を green に保つ。

## 2. 今から意識する「エコノミックな動線」＝ 3 点

新規コードでこの癖を守るだけで、後の最適化が局所変更で済むようになる。

### 2.1 冪等 ＆ 局所更新
- `refresh〇〇()` は「**呼べば必ず正しい状態になる**」形を維持（現状そうなっている）。
- 全再描画ではなく、**変わった行・セルだけ**触る方向へ寄せる。
- DOM の全 `innerHTML` 差し替えは極力避け、既存ノードの textContent / class を更新する。

### 2.2 計算のキャッシュ（メモ化）
- 「同じ入力 → 同じ結果」の重い計算（中央値、売上マップ、比率統計など）は
  入力が変わるまで**使い回す**。
- 実例: L2 は月 × 費目の `rateCache` で同一 lineId/月の再計算を回避済み。今後もこの型を踏襲。

### 2.3 更新のバッチ化（デバウンス／rAF）
- 現状、セル編集のたびに次の連鎖が走る:
  `refreshPlRatios → refreshPlYearTotals → refreshPlReferenceBudget(→L2)`
- 将来ここを `requestAnimationFrame` で **1 フレーム 1 回**にまとめられるよう、
  “差し込み口”を意識しておく（後で 1 箇所直すだけで軽くなる）。
- 連続入力・連続クリック時の多重発火が体感悪化の主因になりやすい。

---

## 3. 「後で軽くする前提」で仕込んでおくと得すること

- **データ層と描画層の分離**
  `localStorage` / gateway の読み書きと DOM 描画を混ぜない。
  分離していれば、後で描画方式（仮想化・部分描画）だけ差し替えられる。
- **計測フックを軽く残す**
  重い関数に `performance.now()` の簡易ログを仕込めるようにしておき、
  「どこが重いか」を**推測でなく数字**で判断する（無駄な最適化を避ける）。

## 4. 既知のホットスポット候補（未着手・観察メモ）

> 断定ではなく「後で計測して確認する候補」。壊さないため今は触らない。

- **refresh 連鎖の多重発火**（2.3）: 入力・年移動・MEP↔PL 同期イベントでの重複呼び出し。
- **`querySelectorAll` の繰り返し**: 明細セル全走査を毎回行う箇所。対象を絞る / 結果を保持する余地。
- **売上マップ再構築**: `plRefBudgetSalesMapFromObject` 等を月ごと・セルごとに再生成している箇所。
- **行高同期 `syncPlSplitLayout`**: 全ペア再測定。描画イベント連発時にまとめられる可能性。
- **MEP 二重注入の掃除**（高リスク）: 既知の重複注入。安全に外せるかは要検証、単独 PR 推奨。

## 5. 進め方の線引き（まとめ）

| 区分 | 方針 |
|------|------|
| **今やる** | 新規コードは 2.1〜2.3 の癖で書く（局所更新・メモ化・必要なら軽いデバウンス） |
| **今やらない** | 既存の広範囲リファクタ。機能が一段落してから小 PR 単位で刻む |
| **常に** | 変更のたびに `verify_pl_*` を green に保つ。壊れたら即戻す |

> 「**新しく書く分はエコに、既存は検証で守りながら後で刻む**」——この二段構えで、
> 速度を追ってデータを壊す事故を防ぐ。
